## Scope and applicability

- What it is: an XML vocabulary for exchanging structured locale data, used by the Unicode Common Locale Data Repository (CLDR). The CLDR home page describes CLDR as three things: curated locale data (dates, numbers, currencies, units, sorting, and more, for over 100 languages), the UTS #35 specification of its structure and use, and the tooling that collects and validates the data.
- Status as printed: reviewed by Unicode members, approved for publication by the Unicode Consortium, a stable document that may be used as reference material or cited as a normative reference by other specifications.
- Document class: the Unicode technical reports page defines a UTS as an independent specification. Conformance to the Unicode Standard does not imply conformance to any UTS. A UTS is therefore normative in its own right for anyone claiming conformance to it. It is not part of the Unicode Standard. (The fetch tool's own gloss, "a UTS is non-normative", misread this definition. The note relies on the quoted definition, not the gloss.)
- Conformance model (Part 1, Conformance): two clauses, printed with the labels UAX35-C1 and UAX35-C2. C1: an implementation that claims conformance identifies the sections it conforms to, interprets LDML elements and attributes as specified, declares which CLDR data types it uses, and declares where it overrides CLDR data or uses alt values. C2: an implementation that claims conformance for locale and language identifiers states whether Unicode locale extensions are allowed and which canonical form it uses. A general claim of conformance covers every portion relevant to the operations the implementation performs.
- Who it binds: implementers of locale data and formatting libraries (ICU, platform i18n APIs, and similar), not application UIs. UTS #35 does not require an application to show locale-appropriate formats. The Part 4 dateFormats section has no MUST or SHOULD about applications choosing locale patterns over hard-coded ones. UI audit rules built on it are therefore project-formulated (BEST_PRACTICE), with CLDR data as the reference oracle. The exception is where the spec states a requirement about the pattern itself, which can be carried over to displayed output (STANDARD).
- Platforms: all (web, pwa, ios, android, desktop). CLDR data backs ICU and, through it, most platform and browser i18n APIs. That backing relationship was not verified in this session (see uncertainties). Jurisdiction: GLOBAL.

Identifier scheme: parts, then numbered sections with HTML anchors, then XML element and attribute names (for example dateFormats, availableFormats, timeData with preferred and allowed hour cycles, weekData with firstDay, minDays, weekendStart, weekendEnd, currencyData, pluralRules, listPatterns, contextTransforms). Part 1 lists the Unicode locale extension (-u-) keys that override locale defaults: ca (calendar), cf (currency format style, standard or accounting), co (collation), cu (currency), fw (first day of week), hc (hour cycle), ms (measurement system), nu (numbering system), rg (region override), sd (subdivision), tz (time zone). Section numbers are not guaranteed to stay stable across revisions, and this was not checked, so rule IDs should use section slugs rather than numbers.

Normative vs informative:
- Normative: the conformance clauses; the XML structure and DTDs; syntax definitions (date field symbols, number pattern syntax, plural rule syntax and operands, MessageFormat ABNF); explicit must and should statements. In Part 4, as read through the fetch tool: 12-hour-cycle time patterns must include a day period field. 24-hour-cycle patterns and skeletons should not include day period characters. A statement that intervals must cover 24 hours with no overlaps (its context, probably day period rules, was not confirmed). Era names should be distinct within each width.
- Informative: examples, background, and "typically" or "can" statements (for example that standard date and time patterns typically come in four lengths: full, long, medium, short).
- Deprecated items are marked in the text: old am and pm elements (replaced by dayPeriods), localized pattern characters, the calendar territories attribute, timezoneData, supplemental-level metazoneInfo, measurement elements, and exemplar mapping and index labels.
- Technical preview: rational number formats in Part 3. In Part 9, MessageFormat functions marked Draft may change.

What the data lets an audit compare against (paraphrased, Parts 2–4):
- Dates and times: four standard lengths plus skeleton-based flexible formats. Field order, separators, and month and weekday names vary by locale. The preferred hour cycle is set per region (H, h, K, k, with B or b flexible day periods allowed), and the user can override it with -u-hc-. Week data gives the first day of the week, the minimal days in the first week, and the weekend span per region, with a precedence order starting from the -u-fw- keyword. Time zone display falls back from a specific zone name to a metazone name, then a region format with the location, then a GMT offset. Relative-time patterns are plural-aware. Interval formats collapse shared fields in date ranges.
- Numbers: locale digits (numbering systems) and symbols (decimal, grouping, percent, signs). Grouping can be variable (for example Indian-style grouping), and minimum grouping digits suppresses separators for short numbers in some locales. Compact formats (for example millions) depend on plural category. Currency patterns place the symbol before or after the number, with extra spacing when the symbol is alphabetic. Supplemental currencyData gives decimal digits and rounding per ISO 4217 code. An accounting style shows negatives in parentheses.
- Plural rules: categories zero, one, two, few, many, other, with a language-specific subset (English uses one and other). Rules use operands defined in Part 3 §6 (n, i, v, w, f among them), with explicit 0 and 1 cases, and there are plural ranges.
- Units: long, short, and narrow widths. Measurement system per territory (metric, US, UK) with category overrides. Paper size per territory. Territory- and usage-based unit preferences (for example person height).
- Lists: locale list patterns by width and position.
- Other: localized display names of languages, regions, and scripts. Paragraph direction via character order. Locale quotation marks. Context-dependent capitalization.
- Locale fallback (Part 1, Locale Inheritance and Matching): lookup from the specific locale toward root through parent locales, lateral inheritance, and region-priority inheritance. Likely subtags fill in missing script and region. Language matching picks the best supported locale for the user's preferences.

## Candidate rules

Proposed prefix: `CLDR` mapped to SRC-UNICODE-UTS35 (alternative `LDML`; the lead decides and records it in `docs/rule-schema.md` §8). IDs use section slugs plus a sequence. Unless marked STANDARD, each rule is project-formulated: the spec supplies the reference data and has no application-level obligation, so the source strength is INFORMATIVE and the project may assign SHOULD. Testing approach for all of them: render the target in at least two locales (or with the relevant -u- keyword) and compare displayed strings with a reference formatter backed by CLDR data (ICU, or the ECMA-402 Intl APIs in the audit browser), pinned to a recorded CLDR version.

Testability notes:
- Oracle version drift: CLDR data changes between releases (for example, 48.2 changed Swiss French number formatting and adjusted some date formats for web compatibility, per the CLDR 48 page). A browser's or OS's Intl output reflects whatever CLDR and ICU version it ships, which may not be 48.2. Automated comparisons should record the oracle's CLDR version and treat differences in a single character (spaces, narrow no-break space, punctuation) as low-confidence, not FAIL.
- Locale detection: a check first has to establish which locale the product claims to serve (UI language, lang attribute, locale switcher, Accept-Language). Without that, a hard-coding finding is only a UX_RISK.
- Screenshots and design files support visual checks only. The strongest method is to render the same state in two or more locales.

## Uncertainties and gaps

1. Conformance clause labels: RESOLVED by the lead and the reviewer on 2026-09-23; the page itself prints UAX35-C1 and UAX35-C2 although the document is a UTS. The statement that day-period rule sets cover 24 hours without overlaps is in Part 4 §4.5 (Day Period Rule Sets), per the reviewer.
2. All content was read through a fetch tool that converts pages to markdown and summarizes them. The Part 4 must and should statements (the day period statements especially), the full list of plural operands, and the lenient-parsing wording need a verbatim re-read in Phase 2 before normalizing.
3. Date alignment: the spec is dated 2026-03-03 and CLDR 48.2 was released 2026-03-17. The download page links 48.2 to revision 78, so this is not a contradiction. CLDR 48.2.1 (2026-07-08) has no spec revision. The CLDR home page summary listed releases up to 48.2 and did not show 48.2.1. This may be a summarization omission; not confirmed.
4. Successor imminent: CLDR 49 (Alpha 2, release shown as 2026-10-XX) will bring a new UTS #35 revision and make revision 78 superseded. Re-verify after the CLDR 49 release, before Phase 2 normalizes any CLDR rule.
5. License: documents may be copied only for personal or internal business use, not public distribution. That rules out verbatim excerpts in a repository that may be public, so paraphrase only. The CLDR 48 page points to copyright.html#Exhibit1, but the current Terms of Use page showed no "Exhibit 1" heading. It does state that Unicode data files and software, including /Public/cldr/, are under the Unicode License v3. The stale anchor is unconfirmed. The Terms page showed no last-updated date.
6. Tier and rule class mapping: the document is T1 as a standard, but it binds formatting implementations, not application UIs. Most UI rules are therefore project-formulated BEST_PRACTICE with INFORMATIVE source strength. After review, every UI rule from this source is BEST_PRACTICE, including the day-period rule, because the spec's requirements bind locale data and implementations, not applications (a STANDARD MUST rule could otherwise produce VIOLATION findings, GAP-026). The tier stays T1 for the document itself.
7. The claim that ICU, platforms, and browsers use CLDR data comes from general knowledge and the CLDR home page's general statement. It was not verified per platform, and ECMA-402's relation to CLDR was not read. Automated oracle comparisons depend on this.
8. Time Data lookup when a locale has no region: the fetch tool said it falls back to region 001. Whether likely subtags are applied first was not confirmed.
9. Address formats: no part of UTS #35 covers postal addresses (the nine-part list has none), so addresses are anchored elsewhere: the lead mapped the GOV.UK Addresses pattern (SRC-GOVUK-DESIGN-SYSTEM) on 2026-09-23. Part 8 Person Names may anchor name display but was not read beyond its title.
10. Parts 5 (Collation), 6 (Supplemental), 7 (Keyboards), and 8 (Person Names) were not read beyond their titles. Their audit relevance (for example locale-correct sorting of lists) is unassessed.
11. Section numbers were taken from the tables of contents as read. Whether they stay stable across revisions was not checked, so IDs use slugs.
12. Prompt injection: no text addressed to an agent was observed in any fetched page. Some fetch-tool summaries added their own "notes to AI agents" headings, and one added implementation advice. These are tool output, not source content, and were disregarded.
